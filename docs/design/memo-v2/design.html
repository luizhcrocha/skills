The admission rule

A line becomes a note when both answers are yes. Will it still be true in a month? Is it absent from the code, the docs, the commits and every plan?

The lineWhere it goes
"Chose TOML front blocks over YAML because tomllib is in the standard library"a note when no doc or commit says it
"The migration landed as 43d10bc8"nothing jj log holds it
"PreCompact wording still untested, waiting on a real compaction"a work item the owner's dossier, ledger or issue
"Never push without a landing turn"a rule AGENTS.md or CLAUDE.md, which every session already reads

memo cannot check a judgement. The rule is in the skill and in the header of every start read, nothing presses a session to write, and memo note answers a commit hash or a look-alike with one line of advice.

Scopes

Every note belongs to exactly one scope. The question that picks it is "who else must read this?".

repo

One repository, any machine

Carried by the memo bookmark of that repository's remote, apart from the code history. The default for memo note.

machine

One computer, any repository

Carried by the memo bookmark of the dotfiles' remote, in machine/<name>/.

group

Repositories that work together

Carried by the same bookmark, in group/<name>/. You defined two groups.

user

You, everywhere

Carried by the same bookmark, in user/.

You define the groups in one file in the dotfiles. You chose two on 2026-11-16, and the migration writes the file with them. Nothing asks you to edit it.

# config/tstack/groups.toml

[groups.company]

  • A repository can be in two groups at most. The groups of a repository share 2,500 bytes, and one note of 280 characters with its heading needs about 425. When the file names a repository in more, memo reads the first two by name and the start read names the others.
  • A note about another repository goes to that repository's store, with memo note --scope repo:<owner>/<name>, when that repository has a store on this machine. Otherwise it goes to a group the two share.
  • memo reads the copy of groups.toml that home-manager installs, never the file in the dotfiles checkout, which another writer can move to an older commit.
  • The machine's name comes from memo.toml, which home-manager writes with the flake's name. It is never the host name, and on the Mac the two differ. Without the file there is no machine scope, and the start read says so.

Today's global store mixes all of this. The migration gives each of its 254 live notes one target: user, a machine, the dotfiles repository (for how the machines are configured), a group, one repository, or retirement.

A slice is a limit, not a quota. A scope with little to say uses less, and no other scope takes the rest. A section never exceeds its slice. The five numbers are constants in the code, the code asserts the total at every start, and a test fails on any path over it. A fleet worker reads nothing, as today.

  • A store over its slice. The oldest notes that no summary stands for leave the read first, and one line counts what is left out. A note that a summary keeps was chosen once, and a burst of new notes does not push it out. It leaves only when the kept notes alone do not fit, which the tasks over the summaries end.
  • The count line. (+11 notes, 2026-09-16..10-08, about hook, statechart, PreCompact: memo zoom BFKX9K) gives the number of notes a summary hides, their dates, and up to 3 of their most distinctive words. memo counts words in the index, with no model: a word scores by the hidden notes that have it, weighed against how common it is in the store. The line can print only words that the hidden notes contain.
  • Time. A record file is never edited, so its name says whether the index is current. At start memo lists file names and parses only new files. On 4,101 notes the names took 1.5 ms, a stat of each file 12 ms, and a read of each file 45 ms.
  • Subfolders. A record sits in notes/<first 4 characters of its id>/, one folder for 12.4 days. A commit that adds one note to a flat folder of 42,000 writes 1.94 MB of git tree objects, against 0.07 MB with the subfolders.

Summaries quote, and the count line names what they hide

You approved older notes shown "as summaries", OptMem's way, and asked for a faithfulness check before the start read relies on them. The check ran on 2026-11-16, with tape's method: an Opus Reviewer compared 30 of the 259 summaries in custom-mcp-servers with the exact lines each was written from. A pending job reads as cancelled. A rule about deletions reads as a rule about deploys. One invented line was copied into the level-2 summary above it. The errors sit where a short item loses its qualifier ("pending", "without Luiz's yes") and where a prefix such as "Luiz:" spreads over items that do not carry it.

So a summary quotes and never rewrites. It names the notes it stands for and, among them, the few to keep in the start read. The read prints those notes word for word and one line that counts the others. Every line a session reads at start is then a line some session wrote on purpose, and a corrected note stops being read the moment it is corrected. This is ADR 0007. You decided it on 2026-11-16 and added the words on the count line.

The price is compression. About 4 lines stand for 12 notes, where one rewritten line stood for 16. The whole read holds about 44 notes. That is what 4k tokens buy, and memo recall is the way to the rest. You kept the group of 12.

Quoted notes state nothing false. Their one fault is a kept note that a later note contradicts. So a compaction task over summaries, whose list spans months, tells the session to retire or supersede such a note before it answers. The rewritten line carries more facts in fewer bytes. The words on the count line pay part of that back: they tell a session what the hidden notes are about.

  a fleet worker                       refused, as today: its coordinator notes for it

A compaction task lists the oldest group of notes outside a summary and asks the session to name up to 3 that a session a month from now most needs. It never blocks a write. A fleet worker gets none. A task over summaries lists the notes that those summaries keep, and it also tells the session to retire or supersede a note that a later note in the list contradicts.

A note's life

Teal states are inside the budget. The orange state is the time between a burst of writes and the compaction tasks that follow. A note behind a summary stays there when the store goes over its slice, because the summary stays in the read. A note leaves the live set only by memo supersede or memo retire, and never comes back.

How notes travel between machines

One rule makes every merge safe. Every note, summary and retirement is a new file with a unique name, and no command edits or deletes a file. So a store is a set that only grows, and two copies merge by set union of their file names. Any number of sessions on any number of machines can write at once. Two writers never touch the same path, so no merge has anything to resolve inside a file.

Every store travels on a memo bookmark

You decided on 2026-11-16 that notes stay out of every code history. A repository's notes are not in its working tree, so they are in no diff, no pull request and no code search. The remote backs them up and shares them on a bookmark named memo, whose history shares no commit with the code. The machine, group and user stores travel the same way, on the memo bookmark of the dotfiles' remote, as the folders user/, machine/<name>/ and group/<name>/ beside the dotfiles' own notes.

A fetch and a push use your SSH key, and 1Password asks you to approve each use. An agent cannot approve, and an unattended push stalls. So memo syncs only where a push that you approve already happens. No hook, no timer and no memo note runs a sync.

The checked model

A TLA+ model of one store on two machines, checked with TLC through the statechart skill. Sessions write notes, write summaries, correct and retire. Machines exchange files directly, or through a bookmark that takes a push only from a machine that holds every file of the bookmark. After each step each machine's start read is computed again. The model ran again on 2026-11-16 after two changes: the new rule for a store over its slice, and the bookmark. Moving the machine, group and user stores to a bookmark changes no rule, and the four runs gave the same results after it.

No note is rewritten and no note is lost. The v2 code reads the old files where they are, so it can land before any data moves, and the start read is inside its budget from that moment.

  1. Snapshot. Each store is copied to a local archive, which memo recall searches. For custom-mcp-servers and global it is the only backup.
  2. Groups. The migration writes groups.toml with the two groups you chose.
  3. An agent pass over the 96 open threads and 16 pins. One Researcher for each store reads every item against the repository, jj log, the ledgers and the dossiers, and one Decider rules on what they cannot place. Each item gets one end: a plain knowledge note in the right scope, a retirement with the evidence that it is done, a line in its owner's record, or a retirement as "unplaced". The owner is found from the session id in the note: a fleet's ledger for a coordinator's note (a note event, which opens no card), a designer's dossier for a designer's.
