# Hotfix

**You own the break until trunk is green again. The smallest fix lands in minutes; the full suite runs after it lands.** Luiz, 2026-11-18: "we can't keep things broken for hours because we are doing a thousand tests".

A hotfix is for a break that is already there and blocks others: a red suite on the landing bookmark's tip, a broken tool the lanes depend on (land-check, fleet, a hook), or production work failing now. A red only on your own stack, or a defect that blocks nobody, is a Bug fix.

1. Red: one command, already run, is red on the break at `<bookmark>@origin` (a production break: on the production surface). Name who it blocks. Tell them you hold it ([FLEETS.md](../FLEETS.md)), so one lane fixes it.
2. Pick the smallest change that turns the command green. A landing caused it and the cause is not in hand in about 10 minutes → revert that landing: `jj revert -r <change> --onto <bookmark>@origin`. Otherwise the fix, in one change: no refactor, no neighbouring fix. A fix that crosses a function boundary or passes about 300 lines is no hotfix: revert, and the fix goes through Bug fix.
3. Describe the change in the repo's form (`jj describe`), with a body line `Hotfix: <the red command>; blocked: <who>`. Then Land's steps 1 and 2 (the bookmark, the turn, fetch and rebase). Land's step 3 is skipped: one change, no janitor.
4. Run the narrow gate, the repro plus the suites the diff touches (tstack: `just test-changed`; elsewhere [WORKERS.md](../WORKERS.md)'s scoped run): `fleet land --gate -b <bookmark> -- sh -c '<repro> && <touched suites>'`. Its pre-gate asks for a review only over about 300 lines or on a sensitive path: then one `/tstack:review`, recorded as Land's step 4 says; else read the diff once yourself. A red the bookmark's tip already has, in code the fix does not touch, is named in the reply and does not stop the hotfix. The break is `fleet` or `land-check` itself → run the repro and the touched suites directly, and say so. Done when the repro is green on the surface it was red on.
5. Land's steps 6 to 8: the verdict, the push, the confirm. `ask` still goes to Luiz: a production hotfix asks for its deploy at once, with what failed, since when and how many, and does not wait for step 6. One "publish your fixes" yes covers the deploys of the fixes it names, not later or wider ones (Luiz, 2026-11-05).
6. In the same turn as the push, start the repo's full gate on the pushed commit as a background run whose exit wakes you: `fleet run -r <pushed commit> -- <the full gate>` (without `fleet`, the gate command in the background). It holds no push hold, so other lanes land meanwhile. Then `tstack:unblock` tells the blocked lanes the fix landed and the full run is in flight.
7. Act on its exit, the same turn. Green → say so to the lanes that were blocked. Red the hotfix caused → yours, at once: a second hotfix when the cause is in hand, else `jj revert` of the hotfix when its red blocks more than the break did. Red it did not cause → its owner, as Land's step 5 says.
8. Open what the speed skipped: the root cause and the failing test through Bug fix when step 2 reverted or landed no test. The repo's extensive tests (end to end, evals, soak) run at the next deploy or release, where the fix is measured.

**Reply:** the red command and who it blocked, the fix or revert, the narrow gate's commands and result, minutes from red to pushed, the full run's state (running, green, or red and what you did), the deploy asked or done, and the follow-ups opened.
