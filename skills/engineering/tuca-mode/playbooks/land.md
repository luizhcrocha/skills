# Land

**You own what reaches the landing bookmark. Shape the stack, prove it, push it.** The default end of every playbook that changes code. A pull request is a different road (Shipping), taken only when Luiz asks for one.

1. Name the landing bookmark from the repo's own docs (`CLAUDE.md`, `AGENTS.md`, `README.md`, the justfile): `master` in most repos, `nix` in dotfiles. Docs silent → `jj bookmark list` and `trunk()`; still ambiguous → ask. Luiz said "leave it for me to land" → do steps 2 to 4, then stop and report the change ids.
2. Take the landing turn. In a fleet, landing happens from the landing workspace (`*-land`, `deploy`); `default` is Luiz's. Under a manager, step 6's verdict is `stop` until the manager gives the fleet the turn (`fleet turn`). `jj git fetch`, then `jj rebase -b @ -d <bookmark>@origin`: the whole branch under `@` moves onto the fresh tip, side branches and merges included (a no-op when nothing moved). Conflicts are resolved in the stack, by intent.
3. Strip narrating comments with `/tstack:no-comments` on the stack's diff (a fresh reader deletes them and fixes what they papered over), then shape the stack with `/tstack:worktree-janitor` (the skill spawns the agent and audits it): split by intent, fixups absorbed, repo-style descriptions, empty `@` on top. Pass the session's `Claude-Session:` trailer when the repo's messages carry one, and a branchy shape only when Luiz asked for one. Done when its audit passes.
4. Review a stack that needs it before landing. It needs one when it has more than about 300 changed lines (lockfiles and generated files left out), or touches a schema or a migration, auth or permissions, a deletion of data, or billing: `/tstack:review`, or `/tstack:interrogate` when the change is contested; a diff over about 2,000 lines also gets review's bug hunt (its token cost is in that skill). Fix what it finds in the owning change, then record it in a fleet: `fleet state <dashboard-dir> event --kind reviewed --findings <N> --changes "<change id>,..." "..."`. Measured over eight fleets (09-26 to 10-09): about a quarter of the fleets' commits were reviewed; reviews found something about two times in three; unreviewed commits needed a later fix more often (7% against 0%). Step 5's `land-check --pre-gate` fails on a stack this size with no `reviewed` event, before the gate takes the slot. It matches the event by change id, so a stack reshaped after its review (step 3's `jj split` on a re-run after a red gate, or a review recorded before step 3) has parts it cannot match: `jj evolog -r <change>` names the reviewed change each new one came from, and the event is re-recorded under the new ids before step 5 (`--kind reviewed --findings 0 --changes "<new ids>" "re-recorded after reshaping: the review of <old ids>"`), or the review runs again when the reshaping changed the code.
5. Run the repo's full gate once, on the merged and rebased stack head, as the repo names it (tstack: `just test`, every suite in parallel; `just validate`; elsewhere the package scripts or the CI config's commands), with the Vitest pool capped. This is the only full-gate run: workers ran only the tests their changes touch (`just test-changed` in tstack), so no suite runs again per worker. On a machine that runs fleets, run it through the gate slot, behind the review check, as one command: `land-check --pre-gate -b <bookmark> && fleet fleets gate run <fleet> --wait 1800 -- just test` (`--as <session name>` when this session serves no fleet). `--pre-gate` exits 1 with a `warning:` when the stack needs a review the ledger does not record: back to step 4 before any gate runs; it exits 1 too when the work under `@` has several heads or nothing to push, and says which (on 10-20 that warning came only at step 6, after four rounds of a 4 to 13 minute gate). Luiz said to land it unreviewed → the gate command alone. It waits for the slot, runs the gate in a memory-capped systemd scope (a quarter of the RAM by default, so two runs go at once; `--mem 50%` for the whole budget, `--mem` or `$FLEET_GATE_MEMORY_MAX` for another cap) that dies whole, frees the slot on any end, and exits with the gate's code. Run as a background job (`run_in_background`), the gate goes inside `gate run` too, never bare: a killed background job leaves its children running. Per-revision checks go through the janitor's `--check` when each change must stand alone. Red → the fix goes to the worker whose change caused it, or into the owning change (`jj squash --into` or `jj absorb`) when no worker holds it, then re-run from step 3.
6. Get the verdict: `land-check --bookmark <bookmark> --apply-skip-ci` (on the Bash PATH; else `scripts/land-check` in the plugin root). Its JSON names the head (the single top revision under `@`), the stack, whether it fast-forwards, whether the push deploys, and the repo's `[skip ci]` habit; when every file is docs, memo notes, tooling or tests and the repo uses the marker, it has appended ` [skip ci]` to the head's subject. Act on `verdict`:
   - `push` → step 7. Its `review` field and a `warning:` or `reminder:` reason say when the stack meets the review threshold with no `reviewed` event: go back to step 4 unless Luiz said to land it unreviewed.
   - `ask` → the push would deploy, or nobody can tell. Stop and ask Luiz, showing `jj log -r '<bookmark>@origin..<head>'` and the `reasons` that name what would deploy.
   - `stop` → several heads: ask which to land, or propose joining them (`jj new <A> <B> -m ...`, then from step 3). Not a fast-forward: a push that rewrites remote history (`--allow-backwards`, a force) is on the pause list, so stop and ask. An undescribed or conflicted revision: back to step 3.
7. Push: `jj bookmark set <bookmark> -r <head>`, then `jj git push --bookmark <bookmark>`. Every push to the landing bookmark needs the turn, a push Luiz approved on the fleet page included: his approval answers "may this land", the turn answers "when" (the plugin's hook denies the push without it). The push goes over SSH through 1Password, which waits for a click; when it stalls, say so and leave the command for Luiz.
8. Confirm: `jj log -r '<bookmark>@origin'` is your head. `@` sits on a fresh empty change (`jj new` if `@` is the pushed commit). Memo notes written during the work land with it.

**Reply:** the bookmark, the landed change ids with their subjects, the review run (or why none was needed) and its findings, the checks run and their result, the janitor's audit verdict and undo line, land-check's verdict with its deploy finding and whether `[skip ci]` went on, and anything left out of the landing.
