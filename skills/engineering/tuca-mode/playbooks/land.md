# Land

**You own what reaches the landing bookmark. Shape the stack, prove it, push it.** The default end of every playbook that changes code. A pull request is a different road (Shipping), taken only when Luiz asks for one.

**A fix for a break that blocks others lands first**, on its own and never chained behind feature work: a red trunk, a broken gate or tool, production work failing now. It takes the [Hotfix](hotfix.md) playbook, not the steps below.

1. Name the landing bookmark from the repo's own docs (`CLAUDE.md`, `AGENTS.md`, `README.md`, the justfile): `master` in most repos, `nix` in dotfiles. Docs silent → `jj bookmark list` and `trunk()`; still ambiguous → ask. Luiz said "leave it for me to land" → do steps 2 and 3, then stop and report the change ids.
2. Take the landing turn. In a fleet, landing happens from the landing workspace (`*-land`, `deploy`); `default` is Luiz's. Under a manager, step 5's verdict is `stop` until the manager gives the fleet the turn (`fleet turn`; with no `fleet` on PATH there is no turn). `jj git fetch`, then `jj rebase -b @ -d <bookmark>@origin`: the whole branch under `@` moves onto the fresh tip, side branches and merges included (a no-op when nothing moved). Conflicts are resolved in the stack, by intent.
3. Strip narrating comments with `/tstack:no-comments` on the stack's diff (a fresh reader deletes them and fixes what they papered over), then shape the stack with `/tstack:worktree-janitor` (the skill spawns the agent and audits it): split by intent, fixups absorbed, repo-style descriptions, empty `@` on top. Pass a branchy shape only when Luiz asked for one, and no attribution trailer (`Claude-Session:` and the like): the push hook refuses one. Done when its audit passes.
4. `land-check -b <bookmark>` says `gate_needed: false` (every file is a Markdown file at the root, or a .md or .txt file in the top-level docs/ or ADR folder) → no gate run: step 5. Otherwise run the repo's full gate once, on the merged and rebased stack head, as the repo names it (tstack: `just test`, every suite in parallel; `just validate`; elsewhere the package scripts or the CI config's commands), with the Vitest pool capped. This is the only full-gate run: workers ran only the tests their changes touch (`just test-changed` in tstack), so no suite runs again per worker. On a machine with `fleet` on PATH, run it as fleet's landing run: `fleet land --gate -b <bookmark> -- <the whole gate command or script>`, which first runs `land-check --pre-gate --require-reviews -b <bookmark>` and the stack's shape check, and on a failure runs nothing and takes no slot. Without `fleet`, run `land-check --pre-gate -b <bookmark>`, then the gate command directly. `--pre-gate` exits 1 when the work under `@` has several heads or nothing to push, and says which (on 10-20 that came only at the verdict, after four rounds of a 4 to 13 minute gate). (`--require-reviews` is accepted and does nothing: no stack needs a recorded review.) The landing run waits its turn, admitted on its estimate (the 90th percentile of its last 10 runs' peaks, with fewer than 5 runs their maximum, times 1.10, 2G at least, a last word naming a revision being no difference; with none, $FLEET_GATE_MEMORY_MAX when set, else the largest peak of the same command, its workspace's root as a placeholder, in the repository's other workspaces over the last 24 h times 1.25, never another repository's, else 25% of the RAM), and a landing gets no place ahead, so a bench ahead of it can still delay it, and one landing per repo runs at a time. Once it passes, it keeps a push hold that blocks only that repo's other landings, until its token is freed or 2 minutes pass. It runs the gate in a systemd scope under the ceiling every run has (MemoryMax half the RAM) that dies whole, with `FLEET_GATE_RUN_CPUS` set to its CPU quota (else the CPU budget), 8 at most, always the run's own, for the repo's config to size its pool by (`maxWorkers: Number(process.env.FLEET_GATE_RUN_CPUS) || 8`); the gate sets no tool's own worker variable (vitest's `VITEST_MAX_WORKERS` overrides a project's `fileParallelism: false`) (Playwright: cap it with `--workers`), logs the machine's pressure (PSI) on the run's record, frees the slot on any end, and exits with the gate's code. Run as a background job (`run_in_background`), the gate goes inside `fleet land --gate` too, never bare: a killed background job leaves its children running. Per-revision checks go through the janitor's `--check` when each change must stand alone. A red proved flaky goes on to step 5, with the post that goes with it (the evidence and the post are in Integrate in the fleet plugin's coordinator skill, INTEGRATE.md). Any other red → the fix goes to the worker whose change caused it, or into the owning change (`jj squash --into` or `jj absorb`) when no worker holds it, then re-run from step 3. A red that fails alone in code the stack does not touch has no owner in the stack and still stops the land: post it to the tests fleet with its log path and tell Luiz.
5. Get the verdict: `land-check --bookmark <bookmark> --apply-skip-ci` (on the Bash PATH; else `scripts/land-check` in the plugin root). Its JSON names the head (the single top revision under `@`), the stack, whether it fast-forwards, whether the push deploys, and the repo's `[skip ci]` habit; when every file is docs, tooling or tests and the repo uses the marker, it has appended ` [skip ci]` to the head's subject. Act on `verdict`:
   - `push` → step 6.
   - `ask` → the push would deploy, or nobody can tell. Ask Luiz in the reply (What needs Luiz), showing `jj log -r '<bookmark>@origin..<head>'` and the `reasons` that name what would deploy.
   - `stop` with `freeze` → another lane's landing gate of this repository is running, or passed and holds the landing turn for its push; a push now sends it back to the gate. Wait for the time its reason names (`fleet gate` shows the hold, when `fleet` is on PATH), then step 2's fetch and rebase; a stack the rebase moved runs step 4 again. After this lane's own `fleet land --gate` run passed, pass `--push-token <the printed token>` so its own hold does not freeze it.
   - `stop` → several heads: ask which to land, or propose joining them (`jj new <A> <B> -m ...`, then from step 3). Not a fast-forward: a push that rewrites remote history (`--allow-backwards`, a force) is on the pause list, so stop and ask. An undescribed or conflicted revision: back to step 3.
6. Push: `jj bookmark set <bookmark> -r <head>`, then `jj git push --bookmark <bookmark>`. Every push to the landing bookmark needs the turn, a push Luiz approved on the fleet page included: his approval answers "may this land", the turn answers "when" (the fleet plugin's hook denies the push without it). The push goes over SSH through 1Password, which waits for a click; when it stalls, ask Luiz in the reply to approve it in 1Password, then push again once he says so. After a `fleet land --gate` run passes it keeps the slot for that repo's landings: push, then free the printed token (`fleet gate free <token>`; no slot, no token, without `fleet`); the hold lapses after 2 minutes. Once `jj git push --bookmark <bookmark>` succeeds, run `memo sync` (on the Bash PATH; skip it on a machine with no `memo`): it carries this repository's notes and the machine, group and user notes to and from their `memo` bookmarks. Offline or unapproved, it says so in one line and exits 0, and the notes wait for the next sync. Then invoke `tstack:unblock` to answer the sessions waiting on this landing.
7. Confirm: `jj log -r '<bookmark>@origin'` is your head. `@` sits on a fresh empty change (`jj new` if `@` is the pushed commit).

**Reply:** the bookmark, the landed change ids with their subjects, the checks run and their result, each flaky test and its post, the janitor's audit verdict and undo line, land-check's verdict with its deploy finding and whether `[skip ci]` went on, and anything left out of the landing.
