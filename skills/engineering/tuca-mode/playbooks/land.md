# Land

**You own what reaches the landing bookmark. Shape the stack, prove it, push it.** The default end of every playbook that changes code. A pull request is a different road (Shipping), taken only when Luiz asks for one.

1. Name the landing bookmark from the repo's own docs (`CLAUDE.md`, `AGENTS.md`, `README.md`, the justfile): `master` in most repos, `nix` in dotfiles. Docs silent → `jj bookmark list` and `trunk()`; still ambiguous → ask. Luiz said "leave it for me to land" → do steps 2 to 4, then stop and report the change ids.
2. Take the landing turn. In a fleet, landing happens from the landing workspace (`*-land`, `deploy`); `default` is Luiz's. Under a manager, step 5's verdict is `stop` until the manager gives the fleet the turn (`fleet turn`). `jj git fetch`, then `jj rebase -b @ -d <bookmark>@origin`: the whole branch under `@` moves onto the fresh tip, side branches and merges included (a no-op when nothing moved). Conflicts are resolved in the stack, by intent.
3. Strip narrating comments with `/tstack:no-comments` on the stack's diff (a fresh reader deletes them and fixes what they papered over), then shape the stack with `/tstack:worktree-janitor` (the skill spawns the agent and audits it): split by intent, fixups absorbed, repo-style descriptions, empty `@` on top. Pass the session's `Claude-Session:` trailer when the repo's messages carry one, and a branchy shape only when Luiz asked for one. Done when its audit passes.
4. Run the repo's full gate once on the stack head, as the repo names it (tstack: `just test`, every suite in parallel; `just validate`; elsewhere the package scripts or the CI config's commands). On a machine that runs fleets, take the gate slot first and free it after, pass or fail: `fleet fleets gate take <fleet> "full gate" --wait 1800` (`--as <session name>` when this session serves no fleet), then `fleet fleets gate free <token>` with the token it printed. Workers already ran the scoped gate (`just test-changed` in tstack), so their suites are not run again per worker; per-revision checks through the janitor's `--check` when each change must stand alone. Red → fix in the owning change (`jj squash --into` or `jj absorb`), then re-run from step 3.
5. Get the verdict: `land-check --bookmark <bookmark> --apply-skip-ci` (on the Bash PATH; else `scripts/land-check` in the plugin root). Its JSON names the head (the single top revision under `@`), the stack, whether it fast-forwards, whether the push deploys, and the repo's `[skip ci]` habit; when every file is docs, memo notes, tooling or tests and the repo uses the marker, it has appended ` [skip ci]` to the head's subject. Act on `verdict`:
   - `push` → step 6.
   - `ask` → the push would deploy, or nobody can tell. Stop and ask Luiz, showing `jj log -r '<bookmark>@origin..<head>'` and the `reasons` that name what would deploy.
   - `stop` → several heads: ask which to land, or propose joining them (`jj new <A> <B> -m ...`, then from step 3). Not a fast-forward: a push that rewrites remote history (`--allow-backwards`, a force) is on the pause list, so stop and ask. An undescribed or conflicted revision: back to step 3.
6. Push: `jj bookmark set <bookmark> -r <head>`, then `jj git push --bookmark <bookmark>`. The push goes over SSH through 1Password, which waits for a click; when it stalls, say so and leave the command for Luiz.
7. Confirm: `jj log -r '<bookmark>@origin'` is your head. `@` sits on a fresh empty change (`jj new` if `@` is the pushed commit). Memo notes written during the work land with it.

**Reply:** the bookmark, the landed change ids with their subjects, the checks run and their result, the janitor's audit verdict and undo line, land-check's verdict with its deploy finding and whether `[skip ci]` went on, and anything left out of the landing.
