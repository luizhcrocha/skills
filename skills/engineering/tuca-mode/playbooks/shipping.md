# Shipping

**You own what merges. Verify each PR independently, merge only the verified run from the root, then keep your hands off the queue.** Matched only when Luiz asks to ship or merge through PRs; the default end of work is Land, which pushes a bookmark with no PR. This is the half after Babysit. GitHub through `gh`, from the main workspace.

1. **Verify every PR independently.** One subagent per PR, not batched: a Verifier ([MODELS.md](../../../productivity/coordinator/MODELS.md)) that did not write the code, in its own jj workspace, exercising the real surface (run the CLI, drive the UI through claude-in-chrome) against parent and head. Each returns `PASS`, `PASS+NOTES` or `FAIL` with its evidence, and you record the verdict (posting it on the PR is a message to people, covered by Luiz's ship request; say so). CI green is not a verdict; an approving bot review is not a verdict.
2. **Merge only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first without `PASS` or `PASS+NOTES`. A verified PR above an unverified one is not mergeable. Report the ceiling as a PR number and what breaks the chain.
3. **Check that each verdict still describes the patch.** Record the verdict's head and base commits and the patch id of the base-to-head diff (`jj diff --from <base> --to <head> --git | git patch-id --stable`). A rebase or retarget rewrites commits and can invalidate a verdict silently. Before merging, compare the recorded patch id with the current one. Changed only in tests, docs or lint config → build both and judge each difference; noise keeps the verdict, with checks re-run fresh. Anything else changed → verify again.
4. **Prepare only the bottom PR.** `jj git fetch`. When the bottom PR is behind trunk, rebase its bookmark onto the trunk tip and push it: that rewrites a pushed branch, so name it in one line first; Luiz's ship request covers the PR branches of this stack, never trunk. Retarget only that PR to trunk (`gh pr edit <n> --base <trunk>`). Re-run step 3 after the push. Descendants stay as they are.
5. **Merge one PR at a time.** Mergeable now → `gh pr merge <n> --squash`. Requirements still running and Luiz asked for merge-when-ready → arm only that PR with `gh pr merge <n> --squash --auto`. Wait for it to merge before preparing the next.
6. **`autoMergeRequest` is not stack readiness.** It says auto-merge was requested for one PR, nothing about descendants or verdicts. Confirm the forge's state for the current bottom PR, and say the state is unknown when the forge cannot report it.
7. **Recompute after every merge.** `jj git fetch`, confirm the merged commit is on trunk, drop the merged PR from the frozen bottom-to-top list, and inspect the new bottom PR's base, head, checks and patch id. Repeat steps 3 to 6 for that one PR.
8. **Watch the frontier until it merges or fails; do not mutate the queue around it.** `scripts/watch-pr/watch-pr --owner <o> --repo <r> --queued-stack --stack-prs <bottom,...>` in the background as the wake, then `gh pr view <n> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` after each wake, until `mergedAt` is set. Hard-fail only on `CLOSED` with no `mergedAt`, a required check `FAILURE` or `CANCELLED` with auto-merge no longer pending, or `UNSTABLE`/`DIRTY` with nothing pending. A long wait runs under `/loop`. A stalled queue is diagnosed before anything changes.
9. **Stop at the ceiling.** Report what merged, the next unverified PR, and what verifying it would take. Extending the run is a new pass from step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what merged, and what the next gap needs.
