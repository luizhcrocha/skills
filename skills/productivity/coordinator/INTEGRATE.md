# Integrate and review

Read from the coordinator's [SKILL.md](SKILL.md) when a milestone's workers are done, before a gate run, a landing, a deploy's gate slot, or a review brief, and when a test goes red.

## Integrate

When a milestone's workers are done: bring each worker's changes into the stack and prune each workspace or hand it to the lane's next worker ([WORKSPACES.md](WORKSPACES.md#integrating-and-pruning)), run the project's checks yourself (types, tests, lint; a quick win), and the full gate once per landing (in tstack, `just test`), on the merged and rebased stack right before the push, behind the review check and through the machine's gate slot (`land-check --pre-gate --require-reviews -b <bookmark> && fleet fleets gate run --as <fleet> --landing --wait 1800 -- just test`: `--pre-gate` exits 1 when the stack needs a review the ledger does not record, and `--require-reviews` when a change's `reviews` entry is not `current`, so it goes to review before the slot is taken; the gate run waits its turn, first come first served, admitted on its estimate (the 90th percentile of its last 10 runs' peaks, with fewer than 5 runs their maximum, times 1.10, 2G at least, a last word naming a revision being no difference; with none, $FLEET_GATE_MEMORY_MAX when set, else the largest peak of the same command, its workspace's root as a placeholder, in the repository's other workspaces over the last 24 h times 1.25, never another repository's, else 25% of the RAM; a `--mem` below the measured peak is raised to that peak, unless a killed run left that peak, and the run says so) within half the RAM and 24 of 32 CPUs; `--landing` gives it no place ahead, so a bench ahead can still delay it, one landing per repo runs at a time, and once it passes it keeps a push hold that blocks only that repo's other landings, until its token is freed or 2 minutes pass; it runs the suite under one ceiling for every run, half the RAM, in a scope that dies whole, with `FLEET_GATE_RUN_CPUS` set to its CPU quota (else the CPU budget), 8 at most, always the run's own, for the repo's config to size its pool by (`maxWorkers: Number(process.env.FLEET_GATE_RUN_CPUS) || 8`); the gate sets no tool's own worker variable (vitest's `VITEST_MAX_WORKERS` overrides a project's `fileParallelism: false`) (Playwright: cap it with `--workers`), logs the machine's pressure (PSI) at the run's start and end and the most it reached on the run's record, and frees its part however it ends; under a manager the plugin's hook denies a full suite run any other way and names the gate run alone, so put the check in front of it; [DASHBOARD.md](DASHBOARD.md), "Fleets and the manager") and with the Vitest pool capped. A `run_in_background` job, yours or a worker's, that starts a server or a suite runs inside `fleet fleets gate run` or a scope (`systemd-run --user --scope --collect -- <command>`): Claude Code's kill of a background job leaves its children running. A failure there goes back to the worker whose change caused it. A worker never runs the whole gate: it runs only the tests its change touches (in tstack, `just test-changed`; the brief's Lane section has the rule for other repos), so name that in its completion criterion. Measured on 2026-10-09, workers spent 86% of their wall time waiting on tools, mostly full gates of 13 minutes and more, and 14% in the model. A worker reruns a load timeout once, alone, since the CPUs are the bottleneck: every load red triaged on 2026-10-20 was a timeout. That rerun never proves a test flaky. The lander proves it with five runs: a red counts as flaky only when the test passes alone five runs of five, and the stack touches neither the code under test nor any test, fixture, helper or config of that suite (a new test that pollutes shared state makes its neighbour fail in the gate and pass alone). A flaky red holds no land (Luiz, 2026-11-01): the land goes on under the approval it needs anyway, and in the same turn you post the test and its log to the tests fleet, which makes it deterministic or removes it. A pass on a rerun closes nothing. Any other red stops the land, and step 5 of the [Land playbook](../../engineering/tuca-mode/playbooks/land.md) routes it. A red the change did not cause goes to the tests fleet as news with its log path, whether the rerun passed or not (`fleet news post --from <your fleet> --to tests --kind fyi "<the test, the failure, the log path>"`), not a direct message: news wakes nobody, and tests triages flakes for every fleet. Whoever ran the test posts: a worker names its post in its report, so you post only the reds of your own runs. A flake tests has already posted a finding for gets no second post: cite that news id when you ask for the landing turn. Resolve anything left at the seams between lanes, mark the milestone done, and move the roadmap's current step forward. A milestone counts as done when its checks pass, a proved flaky red aside, and its reports clear the standards, not when its workers report.

After a `--landing` run passes it keeps the slot for that repo's landings: push, then free the printed token (`fleet fleets gate free <token>`); the hold lapses after 2 minutes.

A docs-only stack skips the gate: when `land-check` says `gate_needed: false`, fast-forward it with no gate run. When `land-check` stops because another lane's landing gate or landing turn holds the same repo, wait for that landing and run `land-check` again: its push follows its pass within minutes, and a push of yours in between makes its push fail after a passed gate.

**Review before landing.** A stack with more than about 300 changed lines (lockfiles and generated files left out), or one that touches a schema or a migration, auth or permissions, a deletion of data, or billing, gets a review before it lands: `tstack:review` (a Reviewer worker), at Deep when the change is contested. A diff over about 2,000 lines also gets review's bug hunt (slices, readers that over-report, a second look, provers given the claim alone), whose token cost the review skill names. Record it with the commit of each change the reviewer read, which its report carries: `fleet state <dashboard-dir> event --kind reviewed --findings <N> --proven <P> --changes "<change>@<commit>,..." "<what was reviewed, with what>"`; a bare change id is refused, since the change's commit at record time may already hold a fold. Fixes go into the owning change, and a fix squashed in after the review is re-checked (`jj interdiff --from <reviewed commit> --to <change>`) and recorded at the commit the re-check read. `land-check` warns when a stack that meets the threshold has a change no review read at its current content: no `reviewed` event for it, or a non-empty interdiff from the reviewed commit (a pure rebase passes). An older event with a bare change id is read at the commit `jj evolog` shows then, labelled `inferred` (tuca-mode's land.md, step 4, says why that transition is lenient). The evidence (eight fleets, 09-26 to 10-09): about 24% of the fleets' commits were reviewed, reviews found something about 64% of the time, and unreviewed commits needed a later fix more often (7% against 0%).

**One review per change, never two.** The lane's review is the change's review: a fresh Reviewer reads the change's full diff, at the change's level ([Review levels](#review-levels)), before the lane hands it to you, and the event records it as `<change>@<commit>`. At landing, `land-check`'s `reviews` says for each change whether that record is `current`, `interdiff` or `missing`. A `current` change gets no second review (a pure rebase is current). An `interdiff` change gets a Quick review of what changed since the recorded commit alone (`land-check --interdiff <change>@<reviewed commit>` prints it). A `missing` change gets the full review. Your own full review of a change the lane already reviewed is only for a high-risk one: a bulk write or deletion in production, a shared Lambda or Worker. Why (Luiz, 2026-11-05, from a retro of about 20 landings): a second review caught real bugs in 2 of 8 changes, and about 2 of the 8 were pure duplicates of the first.

**A production fix takes the fast lane.** A fix for a defect that is failing production work now (files lost, users' reads failing, runs giving up) takes the fast lane: send it to land on its own, marked as a production fix, with the evidence (what failed, since when, how many: PB1011's 8 lost files waited behind feature work on 2026-11-05). It lands ahead of feature work and deploys right after its gate, still with its one review. The deploy still needs Luiz's yes, and one "publish your fixes" yes covers the deploys of the fixes it names, not later or wider ones.

## Review levels

A review has a level (Luiz, 2026-10-16, adapted from Claude Code Review's Quick, Standard and Deep). You pick it when you write the brief and record it on the step.

| Level | For | Who reviews |
| --- | --- | --- |
| Quick | Tests only, docs, timeouts, descriptions, rebases; any re-review after a FIX, which reads only the interdiff. | One Reviewer on Sonnet, reading the diff and the interdiff only. |
| Standard | Ordinary code. | One Reviewer on Opus (the default). |
| Deep | The permission hook, grants, the cloud's edge and write checks, deploys, concurrency and sockets, migrations. | Three Opus finders in parallel, each from one angle (security; concurrency and state; spec and tests), then one verifier that reruns each finding's proof and drops what does not reproduce, in one pass (`tstack:review`, step 7). |

- A Deep finding survives only when a run proves it: a failing test in the repo's own tools, or its own command's output. A claim no one could run is listed as Unproven with its trace, and the coordinator rules on it: a FIX, a follow-up or a decision for Luiz. A verified finding is Important. A Deep review writes no standalone attack or forging scripts: a safety classifier refused that on 2026-10-16, and a refused act is never routed around.
- A FIX goes back to its worker once. A worker past 150k tokens gets no follow-up round, so a fresh worker takes that FIX with the handoff in its brief, at the lane's effort, and that round counts as the once: it is no rerun, and trigger 4's xhigh is for a handoff before the first review. If the second review still returns FIX with an Important finding, an Implementer lane reruns at Opus xhigh as a fresh worker, in place of a third round ([effort escalation](MODELS.md#effort-escalation-and-the-trial)). The rerun's change is new work, so its review has the change's own level. A re-review of a fix to the same worker is Quick, on the interdiff, unless the fix is large or touches Deep ground: then it stays at the change's level.
- **A cap of three rounds.** A change that still gets FIX after its third review (after the rerun, when effort escalation ran) stops being reviewed. It goes to a design check by the advisor (Fable): the patch isn't converging, so the approach may be wrong. The cap forces a decision, never a merge. The grant-record fix took six serial rounds on 2026-10-16.
- **Tags.** A reviewer tags each finding Important, Nit or Pre-existing. A FIX round fixes only Important. Nits go to follow-ups as a count and a list, and never start a FIX round; one is fixed in the stack only when it is a line inside code being changed anyway.
- **Proof.** An Important finding carries its proof: a breaking input, a failing test, or a trace through the code with file and line. Without one it is a question for the worker, not a finding. Why: 350 of the 957 reviews in October's ledgers mention nits, and agents spend fix rounds on them (Luiz, 2026-11-04).
- **Caught by.** An Important finding names the cheapest check that would have caught it with no reader: `type`, `lint`, `test`, `property`, `model`, or `none`, with the rule it breaks in one line. The FIX adds that check, red first, and a rule worth keeping becomes a line in the repo's REVIEW.md. A `lint` seen twice goes to `tstack:lint-evolve`; a `model` goes to the repo's formal specs, or to a decision suggesting `/create-formal-verification-skill`, which only Luiz invokes. This is how review shrinks: a rule pinned by a check needs no reader next time.
- **Re-reviews.** A re-review reports only what is in the interdiff; anything older is Pre-existing and goes to follow-ups. A finding already fixed is never raised again, and a reviewer names a whole bug class once. Anthropic's post on code review (claude.dev/blog/solving-code-review-at-anthropic) reports that with a round cap and diff-only re-review, PRs needing five or more rounds fell from 8.9% to 1.5%, and about 59% of the code flagged on a 50-round PR had been there since the first pass.
- **A repo's REVIEW.md.** When a repo has one at its root, every reviewer and every finder reads it first. It lists what failure looks like in that repo, in a few lines, each naming the check that pins it, or `no check yet`. Add one line per incident. The Spec reader checks that each line the diff touches has its check.
- Why: this week every change got the same Opus review and every FIX a full new round. The grant-record fix took six rounds, one finder at a time. Parallel finders and a verifier aim to find in one pass what serial rounds find one layer at a time. That is a guess until it is measured, so record the rounds per change by level.
