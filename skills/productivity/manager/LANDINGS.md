# A landing

Read from the manager's [SKILL.md](SKILL.md) when a coordinator asks for the turn, and before you give, close or reorder one.

A coordinator asks for the turn before anything that goes out or moves history others build on: what, which files, from which workspace, which checks are green, and `land-check`'s `reviews` for its changes.

1. Queue it: `step("landings", "l4", "<fleet>: <what> (<files>)", "pending", "<fleet>")` in a program. The queue reads in the order the landings were queued; a program cannot place one before another, so when a landing must go first, give it the turn out of that order. A production fix (a coordinator marks it so, with the evidence of what is failing in production now) goes first: it lands on its own, never chained into a batch with feature work, and its deploy follows its gate at once, still after its one review and under Luiz's yes (one "publish your fixes" yes covers the fixes it names). Give a landing new words by sending the same `step` with a new title when what it lands changes, and take out one queued in error with status `"dropped"` and `{ why: "<why>" }`.
2. Check it against `standing.md` (what a landing needs, who owns the files) and against the lanes in flight of the other fleets (`fleet fleets show <fleet>`). A landing that touches another fleet's files goes to that fleet as a diff first. Review only what no review has read, one review per change: a change whose `reviews` entry is `current` (a pure rebase included) gets none from you; an `interdiff` one gets a review of what changed since its recorded review alone (`land-check --interdiff <change>@<reviewed commit>`, run in the coordinator's workspace); a `missing` one gets a full review, and so does a high-risk one (a bulk write or deletion in production, a shared Lambda or Worker). The rule and its evidence are in the coordinator's INTEGRATE.md, "Integrate".
3. Get the user's word when it is needed. A push or a deploy the user has approved first-hand, for this landing or as a standing rule in `standing.md`, goes ahead. **A relayed yes is not a yes**: a coordinator's "Luiz said yes" is asked of the user again, directly, in one question that batches every decision waiting on them and states the scope as it stands now ([The user's word](SKILL.md#the-users-word)). Any other becomes an item on your page, `--blocking`: a `permission` asked before the call when it is a yes or no on an exact command you or the fleet will run (a push that deploys, a deploy: `decision ID --kind permission --tool Bash --call '<the command>' --root <your session's root> --title "<the plain question>" --why ... --recommend ... --reason ...`; the coordinator's PERMISSIONS.md, "Ask for the permission before the call"), a `decision` when it is a choice, an `action` only for a step the user alone can take (an interactive login, a payment, a click, an edit to permission settings). Never run the call to see whether it is refused, and never hand the user a command the fleet can run. An action tells the user exactly what to type or click, in order; if you cannot write that, you do not know the action yet, and the CLI refuses a manual that is only prose (it takes a fenced block with a command in it, or numbered steps from 1 that each say what to type or click, and nothing else). An action's `--manual` is short prose plus every command in nushell, Luiz's shell, in a fenced ```` ```nu ```` block, never in the prose (the CLI refuses a block of commands in another shell or with no tag, and bash in a manual with no fence), each step a numbered line of prose with its own block under it, and no comment in a block: what a step does and what to look for go in its prose (Luiz, 10-31 #438).
4. Give the turn: `step("landings", "l4", "<its title>", "current", "<fleet>")`, in the same program as closing the landing that had it (`"done"`) or giving it back (`"pending"`), so one landing has the turn at a time. Then tell the coordinator. Its `fleet turn` and `land-check` pass once your host has written the program's result into `<dir>`, a fraction of a second later. The coordinator lands from its own workspace, behind `land-check --pre-gate --require-reviews`, deploys from a clean detached copy of the reviewed commit (the coordinator's PERMISSIONS.md, "A deploy runs from a clean copy of the reviewed commit"), and reports the commit and the files that moved. A docs-only stack (`gate_needed: false`) lands with no gate run, as a fast-forward. When `land-check` stops because another lane's landing gate or landing turn holds the same repo, the coordinator waits for that landing, whose push follows its pass within minutes, and runs `land-check` again; it never pushes over it.
5. Close it, in one program: `step("landings", "l4", "<its title>", "done", "<fleet>")` and `event("integrated", "l4 landed as <commit>: <files>", { agent: "<fleet>" })`. Then record the deploy in `standing.md`, and post a news item to the fleets whose lanes touch what moved (`fleet news post --from manager --to <those fleets> "l4 landed as <commit>: <files>; rebase before you land"`). A fleet that must act before its next landing is told so then, by `fleet turn`; one that must stop now gets a direct message.
