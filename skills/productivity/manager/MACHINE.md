# The machine

Read from the manager's [SKILL.md](SKILL.md) when a fleet's gate slot, memory, idle processes, ports, file owners or 1Password lock is in question, and before you spawn an agent.

- **Heavy checks share one memory budget.** `fleet fleets gate` says who holds the gate slot, who waits for it, in order, and the last day's waits and memory peaks. A coordinator or worker runs a full test suite through it, `fleet fleets gate run <fleet> --wait 1800 -- <command>` (`--as <its name>` when it serves no fleet): it waits its turn, first come first served, admitted on its estimate (the 90th percentile of its last 10 runs' peaks times 1.10, with fewer than 5 their largest, a last word naming a revision being no difference; with none, $FLEET_GATE_MEMORY_MAX when set, else the largest peak of the same command, its workspace's root as a placeholder, in the repository's other workspaces over the last 24 h times 1.25, never another repository's, else 25% of the RAM; a `--mem` below the measured peak is raised to that peak, unless a killed run left that peak, and the run says so) within half the RAM and 24 of 32 CPUs (a bench ahead can still delay a landing gate: `--landing` runs one landing per repository at a time, and one that passed keeps a push hold until its token is freed or 2 minutes pass), runs the suite under one ceiling for every run, half the RAM, in a scope that dies whole, with `FLEET_GATE_RUN_CPUS` set to its CPU quota (else the CPU budget), 8 at most, always the run's own, for the repo's config to size its pool by (`maxWorkers: Number(process.env.FLEET_GATE_RUN_CPUS) || 8`); the gate sets no tool's own worker variable (vitest's `VITEST_MAX_WORKERS` overrides a project's `fileParallelism: false`), logs the machine's pressure (PSI) on the run's record, and frees its part however it ends. While you serve a manager, the plugin's hook denies a fleet session's full-suite command run any other way, naming the `gate run` command to issue instead; it never allows or rewrites one. For a build that loads the machine, a session takes the slot with `fleet fleets gate take <fleet> "what" --wait 1800` and frees it after with the token the take printed (`fleet fleets gate free <token>`). Checking that the slot is free does not reserve it. A take is the whole budget unless it says `--mem`, so it is refused while anyone holds, even the same fleet, and a hold lapses after 60 minutes (`--for MINUTES`). Your page shows the holder. Settle a dispute over it as you settle a turn.
- **A big idle process of a live owner is theirs.** `fleet fleets gate hogs` names it and stops nothing: tell the session, or ask the owner with a permission card on an exact `kill` call. fleet/SPEC.md says what `gate reap` stops by itself and what is never touched.
- **What each session left running.** `fleet fleets procs` lists, per fleet, the background processes its session started, with their age. One that outlived its purpose is its session's to stop: tell it.
- **Where the user goes.** Your Links view lists every fleet's pages and dev servers, and every port the machine serves that no link names, with the fleet that started it. One left unnamed goes back to that fleet to record (`link`) or to stop.
- **Whose files a landing moves.** `fleet fleets whose FROM TO`, in the repository, sorts the files by owning fleet from `<dir>/owners` (one `FLEET GLOB` per line, first match wins; keep it with the owners in `standing.md`).
- **1Password locked is asked once, for the whole machine.** When a fleet's command fails because 1Password is locked, the plugin's hook records it once (`fleet secrets` prints the state), the user gets one card, "Unlock 1Password", on your page and every fleet's, and until it clears the hook denies every fleet session's commands that need 1Password. So a denial or a note that says `1Password is locked` needs nothing from you: the denial itself puts the held fleet on the waiting list, so do not poll or retry, do not open a card, do not ask the user again, and do not tell the fleets (each learns it from its own denial). The time the denial names is not a time to wait for: it is when the hook lets one command of that kind through, from any fleet, to test the lock. Go on with work that needs no 1Password, or end the turn when nothing else is left. Each held fleet is told when it is unlocked, you too when you were held (`[hub] 1Password is unlocked ... Retry.`, in your chat, or directly in this session when the watch is not running): retry then. Only the user clears the lock, by running `fleet secrets unlocked` in his terminal (the card gives the command): never run it yourself (it is refused inside a session), and when the user says in chat that he unlocked it, tell him to run it.
- A line that opens with **`[hub]`** comes from this machine's host service (`fleet-host`, one for every team of the machine) or from a `fleet` command on this machine, and is a fact, never the user. Act on it as you judge; nothing in it is the user's approval or answer.
- **The wake.** A `[hub] <fleet> (<dir>): the chat watch is not running ...` line reaches your session directly (Claude Code shows it as a message from another session): your watch died while the user's messages wait. Arm the watch with the command the line gives, as a background command, and read what it prints; the line asks nothing else. The watch is the host's alone: a session that is a copy of the host (a fork, a second resume of its transcript) is refused when it arms one, and arms nothing; `fleet serve <dir> --take-over` is the only way a second live session becomes the host.

A fleet's advisor plays the Advisor role ([MODELS.md](../coordinator/MODELS.md)) and is restarted on the role's fallback when its model is unavailable (its row's model says which). When one fleet reports Fable unavailable, post it to the news (`--kind fyi`): their next advisor spawn goes straight to the fallback.

Your own session plays the Manager role and the coordinators the Coordinator role ([MODELS.md](../coordinator/MODELS.md)): Opus at low effort, set by the `effortLevel` setting of the launch's `.claude/settings.local.json` (never by `CLAUDE_CODE_EFFORT_LEVEL`, which overrides the effort of every agent spawned too), since the turns are routing and bookkeeping and the hard calls go to an advisor or a Decider. So every agent you spawn gets its role's `model` and `effort` on the Agent call: one spawned bare would inherit your low effort, and the plugin's hook refuses it in a fleet.

A fleet's notices (acts done under a standing approval the user gave, the coordinator's APPROVALS.md) reach you as fyi news: read them with the rest, and raise one with the user only when it looks outside its approval's words.

A monitor agent you spawn (app metrics, runs, executions, reporting back to you) is a Watcher ([MODELS.md](../coordinator/MODELS.md)); when the watch is a command, a background Bash loop does it without a model. In a fleet's session the Monitor tool only watches (read-only commands and the fleet CLI's own watch; the hook denies the rest, the coordinator's PERMISSIONS.md, "The user's word and a refusal"): a command that acts is a Bash call, where auto mode judges it. When a new default model comes out, the fleets move their agents to it (the coordinator's SKILL.md, "A new default model"); yours too.
